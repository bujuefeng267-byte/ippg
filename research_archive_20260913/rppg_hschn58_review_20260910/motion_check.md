# hschn58/rPPG：像素跟踪与动态 ROI 静态核查

核查日期：2026-09-10。固定提交：`8dd44360d159eccde7f85a5a6542e3b44c621029`。仅阅读源码；没有导入或运行上游脚本，没有分析用户视频，因此下述结果不能作为实际精度或覆盖率测量。

## 结论

值得借鉴的是“跟踪同一皮肤像素，再提取颜色时间序列”和“前后向光流一致性检查”。仓库中两个 `temporal_pixel_matching` 脚本确实实现了前后向 LK；`dynamic_roi.py` 的注释与实际实现则有明显差异，并存在影响可运行性、选点及时间对齐的问题。它们不适合直接替换现有项目的连续性处理。

## 两个 temporal_pixel_matching 脚本

源码：[regions](https://github.com/hschn58/rPPG/blob/8dd44360d159eccde7f85a5a6542e3b44c621029/Full_Stack/motion_process/temporal_pixel_matching/forward_backward_pixel_matching_regions.py)、[wholeface](https://github.com/hschn58/rPPG/blob/8dd44360d159eccde7f85a5a6542e3b44c621029/Full_Stack/motion_process/temporal_pixel_matching/forward_backward_pixel_matching_wholeface.py)。

- **前后向检查确实存在。** regions:109–119、wholeface:133–145 依次计算前向和反向 LK，要求两个 status 成功且 `0.00001 < FB error < 0.5` 像素。下限会排除非常接近零误差的点，是否必要需要验证，不能把“越接近零越好”的通常直觉套在当前规则上。
- **它们都是从第一帧播种、一直跟踪到末帧。** regions:125–139、wholeface:150–164 只会减少有效点，不重播种；仅保存全长、无 `None` 的轨迹。短暂遮挡也会让整条轨迹失去最终资格。对于长运动视频，这个选择会产生连续性风险；未运行，不能给出损失百分比。
- **空轨迹未完整处理。** 两者未在所有点失效后提前终止并安全返回，仍会继续把空点集交给 LK；regions:195 还直接读取 `trajectories_db[0]`。虽有“不保存空 NPZ”的分支，但这不等于完整的空结果处理。
- **regions 的五区域不是 FaceMesh 解剖定位。** `get_region_seeds` 使用 `params` 中按给定 bbox 比例得到的下巴/面颊坐标，调用处直接将整张输入图像设为 bbox；效果依赖此前是否正确裁成人脸图像。`GRID_SIDE=20` 配合包含终点的 arange 实际产生 21×21 个点，注释中的 9×9 不准确。
- **wholeface 是颜色接近整幅输入图像均值的随机种子。** 不含独立皮肤分割，输入若含背景则种子并无必然落在皮肤上的保证。未固定随机种子；末尾预览又重新随机抽取一次，因此图上的种子不一定就是刚刚实际跟踪的种子。
- **位置/颜色字段名称需核实。** 两者保存的字段叫 `rgb`，但明确按 BGR 输入解释灰度转换，并把输入的三通道原样保存。名称不意味着进行了 RGB 转换。wholeface 的记录还没有 `region` 键，不能直接喂给按 region 分组的后端。

## BGR/RGB 与现有项目的关系

`Video_get_to_npy/basic_to_npy.py:287–295, 304, 205–223` 从 OpenCV 读取 BGR、原样存入列表；353–354 使用 pickle 写入 `.npy` 扩展名文件。它不为 `dynamic_roi.py` 转成 RGB。后者却在 168、192、148 将输入视为 RGB，并向 MediaPipe 直接传图。**如果直接连接这个采集输出和动态 ROI 脚本，颜色约定不一致。** 这不等于所有上游使用方式都错：若用户自行转换输入，则另当别论；接入前应明确定义颜色顺序和实际存储格式。

对当前项目可尝试的改造应是独立模块：短窗口前后向跟踪 + 越界/空集检查 + 遮挡后的重新播种，并保留帧时间、有效点数和拒绝原因。轨迹丢失后是否保留前段应明确制定规则。随后在同一组原始视频、同一参考对齐和同一评估口径下比较 MAE、有效输出比例与覆盖准确率，而不能根据“光流更复杂”推断精度会提高。
